# Сверка заказов маркетплейса с номенклатурой 1С

Небольшой PHP 8.1+ модуль обмена без фреймворка и внешних зависимостей. Он читает JSON как адаптер API, читает CSV 1С, сопоставляет строки, резервирует остаток и формирует CSV, который можно открыть в Excel. В проект уже включены исходные данные из задания.

## Быстрый запуск

Нужен только PHP 8.1 или новее.

```powershell
php bin/reconcile.php data/orders.json data/nomenclature_1c.csv
php bugs/OrderTotal.php
php tests/smoke.php
```

Первая команда создаёт:

- `output/reconciliation_report.csv` — полный построчный отчёт из 54 строк;
- `output/reconciliation.log` — предупреждения об ошибочных/неоднозначных данных.

Необязательные третий и четвёртый аргументы позволяют задать пути отчёта и лога:

```powershell
php bin/reconcile.php data/orders.json data/nomenclature_1c.csv output/my-report.csv output/my-run.log
```

## Что проверяется

Помимо запрошенных условий, модуль проверяет пустые заказы, пустой/некорректный итог заказа, несовпадение итога с суммой строк, некорректные SKU/количество/цену и неподдерживаемый статус. Номера SKU нормализуются (`trim` + верхний регистр), поэтому ` ts-1002` корректно сопоставляется с `TS-1002`.

Денежные значения приводятся к целому количеству копеек, поэтому цена сравнивается без ошибок `float`. CSV 1С понимает десятичную запятую, неразрывный пробел и пробел как разделитель тысяч.

Ошибочная одна строка не останавливает обработку: она остаётся в отчёте с `HOLD_*`, а контекст попадает в лог. Невозможность прочитать весь входной файл (например, битый JSON) считается фатальной ошибкой процесса с ненулевым кодом выхода.

## Принятые правила

- **Дубль заказа** — повторный `id`. Первый заказ в порядке ответа API — источник истины; повтор с тем же содержимым имеет `DUPLICATE_ORDER_EXACT`, с другим — `DUPLICATE_ORDER_ID_CONFLICT`. Повтор не передаётся и не резервирует товар.
- **Дубль номенклатуры 1С** — один SKU в нескольких карточках. Такой SKU не выбирается произвольно: строка блокируется `NOMENCLATURE_DUPLICATE`, пока карточки не будут исправлены в 1С.
- **Остатки** рассчитываются суммарно и последовательно в порядке ответа API, а не отдельно для каждого заказа. Это исключает ситуацию, когда несколько заказов по отдельности «проходят», но вместе превышают остаток. В отчёте после действия приведён накопленный резерв (`reserved`).
- В резерв попадают только активные (`new`, `confirmed`), не повторные, валидные строки заказа с корректным итогом. Строка с расхождением цены всё ещё учитывается в резерве: потребность в конкретном товаре известна, но её действие остаётся `HOLD_FIX_ORDER_DATA`, поэтому автоматическая передача не произойдёт.
- **Отменённые** заказы показываются в отчёте, но не резервируют и не передаются (`DO_NOT_TRANSFER_CANCELLED`).
- Любое расхождение цены, отсутствие товара, нехватка остатка, невалидная строка или неверный итог останавливает автоматическую передачу только затронутой строки; у менеджера есть конкретное действие в поле `action`.

## Результат на приложенных данных

Сводка ожидаемого запуска находится в [output/example_summary.txt](output/example_summary.txt), а все строки, требующие реакции менеджера, — в [output/example_attention_report.csv](output/example_attention_report.csv). Полный отчёт с готовыми к передаче строками создаётся командой выше.

Найдены: два отсутствующих артикула (`TS-1099`, `TS-2001`), три расхождения цены, четыре случая нехватки с учётом накопленного резерва, один точный дубль заказа, одна дубль-карточка в 1С, один отменённый, один пустой и один повреждённый заказ. Пример лога: [output/example.log](output/example.log).

## Устройство

```text
bin/reconcile.php                    CLI composition root
src/Infrastructure/JsonOrderSource   адаптер текущего «API-файла»
src/Infrastructure/NomenclatureCsvReader
src/Application/ReconciliationService бизнес-правила сверки и резерва
src/Reporting/CsvReportWriter         отчёт для менеджера
src/Support                           логирование и точная работа с деньгами
```

Чтобы подключить настоящий API, достаточно добавить HTTP-реализацию источника заказов с тем же контрактом `fetch(): array`; правила сверки и формат отчёта останутся неизменными.

## Исправления учебного класса

Исправленный файл — [bugs/OrderTotal.php](bugs/OrderTotal.php). Также отдельные пояснения находятся в [bugs/EXPLANATION.md](bugs/EXPLANATION.md).

1. В `subtotal()` цена приводилась к `int`, из-за чего отбрасывалась дробная часть и занижалась сумма заказа.
2. В `vatIncluded()` применялась формула НДС, начисляемого сверху (`20 / 100`), хотя он уже включён в цену. Правильная доля НДС при ставке 20% — `20 / 120` от итоговой суммы.
3. В `calculate()` НДС выделялся из суммы до скидки. Теперь он считается из `total` после скидки, иначе НДС не уменьшался вместе со скидкой.

Самопроверка из условия и дополнительный интеграционный smoke-тест запускаются командами выше.
